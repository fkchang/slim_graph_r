# Authoring SlimGraphR

- Bar: `diagram :bar, title:, unit:` with 2–12 ordered `category id, label, value, focal: false` calls. Orientation defaults to vertical; choose horizontal explicitly. Auto scale contains zero and constant data discloses its reference domain. Zero is labelled and has no rectangle.
- Line: `diagram :line, title:, unit:` with one required `x_axis :time|:ordinal, domain:` and 1–4 series. Every series has one `point value` or `gap reason:` at all 3–24 positions. Time is strict ascending `YYYY-MM-DD` and elapsed-day spaced; ordinal is equally spaced and visibly identified.
- Scatter: `diagram :scatter, title:, x_unit:, y_unit:` with required `x_scale` and `y_scale` and 2–30 complete points. Use at most one focal point and three `annotate: true` labels. Position is the sole encoding.
- Quantitative values are exactly finite Ruby `Integer`, `Float`, or `BigDecimal`. Missing is not zero. Labels use renderer-owned plain half-even formatting with `precision: 0..6`; original values drive finite linear geometry.

Use `require 'slim_graph_r/stream_weaver'` in a StreamWeaver document, then `diagram :type, title: '...' do ... end`. Outside StreamWeaver, use `SlimGraphR.diagram` and call `to_svg` or `to_html`.

- Architecture: `node :api, 'API', detail: 'Request handling', emphasis: true`; `store :db`; `external :client`; `flow :client, :api, :db`.
- Flowchart: `start :request`; `step :draft`; `decision :review, 'Ready?'`; `edge :review, :publish, 'Yes'`. Declare all nodes first or later in the same block. Label every decision exit (max three). `merge :joined` is a visible junction dot with two or three inputs and one output; `finish :done` ends the flow. Start has no inputs; finish has no outputs.
- Sequence: `participant :client`; `message :client, :server, 'Request'`; `reply :server, :client, 'Result'`; `notify` for async. `activate :server do ... end` scopes control. `alt` contains two `branch 'guard'` blocks; `opt 'guard'` and `loop 'guard'` each take a block. These describe control; loop evaluates once. Five participants/twelve messages, one alt or two opt/loop frames, no nested frames. See [sequence guide](sequence.md).
- Timeline: `event '2026-02-04', 'Ship', detail: 'Release the renderer', emphasis: true`. `scale: :date` requires complete Gregorian YYYY-MM-DD dates, sorts them, and preserves exact positions. Same-day events share a marker. `scale: :ordered` preserves caption order; `:auto` uses dates only when every value is valid. Split dense timelines on LayoutError; never alter dates to make the picture fit. See [timeline.md](timeline.md).
- Org chart: use `owner :id, 'Name', invoke: '@route', scope: 'Responsibility', unavailable: true, detail: 'Optional detail', emphasis: true` for accountable people or teams. `owner` uses the same human-facing label slot as `node`; generic `node` calls remain valid and accept the same org-only fields. Connect reporting with `edge`; use `escalation 'Unowned work', to: :owner_id` and `approval 'Production release', by: :owner_id` for footer rules. A child has at most one parent, cycles fail, forests are valid, and the org-specific limits are 12 visible nodes, four tiers, five direct reports per parent, one emphasized node, and two combined rules. Invoke/scope cannot be blank and unavailable must be boolean. Use the [org-chart guide](org-charts.md) and its [Ruby](../examples/standalone/org_ownership.rb) and [JSON](../examples/standalone/org_ownership.json) contracts.
- State machine: use `state :draft, 'Draft'`, `initial :draft`, `final :published`, and `transition :draft, :review, on: 'submit', guard: 'complete?', action: 'queue'`. Transition labels read `event [guard] / action`; `guard` and `action` are optional. Use `direction: :right` or `:down`. The bounded model has two to twelve states, one initial, one or two finals, one simple two-to-four-state cycle, and lifecycle reachability in both directions. In a StreamWeaver document, call `state(:draft, 'Draft')` with parentheses because `state` is a bridge lexical binding. Ruby and strict JSON use the same model; see the [state-machine guide](state-machines.md) and [standalone Ruby](../examples/standalone/state_machine.rb)/[JSON](../examples/standalone/state_machine.json) contracts.
- Dependency graph: use `dependency :app, 'Application'`; use `external_dependency :rack, 'Rack', version: '3.2.1', registry: 'RubyGems'`; connect with `depends_on :app, :rack`. Arrows always run dependent→requirement. Every node gets a computed fan-in badge, including `0 in` for entry points with no dependents; `cycle: true` is allowed on at most one edge only when it closes a real cycle. External treatment takes precedence when an external node is also a leaf. The bounded model allows 9 nodes, 14 edges, four ranks, and no emphasis, groups, or details. One-parent branching hierarchies use `:tree` with nested `root`/`child` blocks; its strict JSON input is the recursive `root` schema in [trees.md](trees.md). See the [dependency guide](dependencies.md) for strict JSON, CLI, and layout limits.
- Tree: use `diagram :tree, direction: :down` with one nested `root :platform, 'Platform' do ... end`; add direct reports with `child :api, 'API', detail: 'Public boundary', focal: true`. `direction: :right` is also supported. A tree requires one root, has depth 1–4 including the root, at most five nodes per tier and five children per parent, and allows zero or one focal node. See [trees.md](trees.md) for the recursive JSON schema and CLI forms.
- Nested containment: use `diagram :nested` with one `scope` chain of 3–5 levels. The innermost scope is automatically focal; nested and layer-stack diagrams use fixed `:down` direction. See [nested-containment.md](nested-containment.md) for strict JSON and limits.
- Layer stack: use `diagram :layers, axis: 'Abstraction', indicator: :up` with 4–6 `layer` calls. Each layer requires `index:`; mark exactly one `focal: true`. Numeric indices such as `L4`, `L3`, `L2`, `L1` are contiguous by one, while all-semantic indices are allowed when unique. See [layer-stacks.md](layer-stacks.md) for strict JSON and limits.
- Pyramid / Funnel: use `diagram :pyramid` with 4–6 `level` calls. Defaults are `orientation: :pyramid` and `mode: :hierarchy` in both Ruby and JSON. Hierarchy is ordinal and accepts no quantities; measured mode requires `unit:` plus chained `from:`/`to:` values, preserves equal plateaus and zero tails, and keeps widths proportional. Use `orientation: :funnel` only with measured mode. A focal level is optional but cannot be the base; narrow measured labels move to outside leaders without changing the true band width. See [pyramids.md](pyramids.md).
- Medallion: use `diagram :medallion` with 3–6 `tier` calls, exactly one `focal: true`, optional final `archive: true`, adjacent `promote` calls, and zero to two `write_path` cards. Each tier requires `bucket:`, `tool:`, `format:`, `writer:`, and one or two `examples:`. Use at most two semantic `concern:` values from `security`, `quality`, `product`, and `analysis`; incoming concern color matches the target, focal styling wins, and an archive landing uses the dashed lifecycle treatment. Write-path tags, titles, and details use measured lanes. See [medallions.md](medallions.md).
- Gantt: use `diagram :gantt` with non-nested `phase` blocks containing `task` records with complete Gregorian `start:`/`finish:` dates. Tasks are exact half-open `[start, finish)` bars; add top-level `milestone` points (an optional `phase:` is milestone-only) and static `marker` points (markers never accept `phase:`). Keep declaration order; no dependencies, critical path, progress, baselines, recurring work, or automatic “today”. The bounded model allows 0–4 phases, 0–12 tasks, up to 8 milestones, 0–2 markers, and one focal task; same-track milestone diamonds must not overlap within 12px. See [gantt.md](gantt.md).
- Kanban: use `diagram :kanban` with 2–5 declaration-ordered `column` blocks and nested `card` records. `state:` defaults to `:default` and may be `:blocked`, `:waiting`, or `:done`; `ticket:`, `owner:`, `focal:`, and positive `wip_limit:` are optional. Counts are derived from displayed cards; a supplied WIP limit renders honest `n/limit` violations, cards remain in source order, and no connectors or inferred states are added. The bounded model allows 0–4 cards per column, 0–12 total, and one focal card. See [kanban.md](kanban.md).
- User journey: use `diagram :journey, persona: 'Analyst'` with 2–6 declaration-ordered `stage` blocks. Each stage requires one explicit ordinal `sentiment:` (`:high`, `:medium_high`, `:neutral`, `:medium_low`, or `:low`) and exactly one `action`; `touchpoint:` is optional and `pain` is limited to the unique lowest-sentiment trough, with at most two pain markers. The curve communicates sequence only, never a continuous score. See [journeys.md](journeys.md).
- User story map: use `diagram :story_map, persona: 'Analyst'` with 2–5 ordered `activity` blocks containing one or two `step`s, then 2–3 `release` blocks. Every release needs a story referencing an activity; exactly one non-final release has `cut: true`. Story `estimate:` and `ticket:` are authored metadata, and at most one story may use `risk: true`; date-like release labels remain literal text. The bounded model allows 12 stories total and four per release. See [story-maps.md](story-maps.md).
- Data flow: use `diagram :data_flow` with 2–4 keyed `role`s, 2–6 ordered `step`s, and 2–16 `transfer`s. Each transfer owns one role/stage cell, requires `tool:`, and may declare `input:`/`output:` as `:web`, `:dataset`, `:table`, `:file`, or `:stream`; omitted payload sides remain undeclared. Add `handoff` with `kind: :ordinary`, `:trigger`, `:focal`, or `:publish`; triggers stay in the same step and follow downward role order, ordinary/publish handoffs advance, and the focal handoff crosses roles and targets the focal transfer in the focal step. Exactly one linked focal claim is required; only it accepts an uppercase `label:`. See [data-flows.md](data-flows.md).
- DP integration: use `diagram :dp_integration` with sources, one platform zone containing ordered bars and one row, consumers, layer services, and explicit `wire`s. Wires use `:ordinary`, `:federated`, `:trigger`, or `:serve`; ordinary wires stay neutral, triggers are unlabelled, and serve wires require the serving component and a protocol. See [platform-integrations.md](platform-integrations.md).
- DP security matrix: use `diagram :dp_security_matrix` with 2–5 labelled `role`s, 2–10 labelled `component`s, and exactly one explicit `permission` for every pair (4–36 cells). Levels are `:admin`, `:write`, `:read`, `:deny`, and `:unknown`; omitted permission labels use only the level default. Unknown, denial, and omission are distinct, and omission fails. Optional role `code:` and component `hint:` remain authored metadata. At most one permission is focal, and only it may carry `note:`. The SVG has no connectors. See [access-matrices.md](access-matrices.md).
- Entity relationship: use `diagram :er` with `entity :customer, 'Customer' do ... end`, nested `field :customer_id, 'customer_id', key: :primary`, and `relationship :customer, :order, from: '1', to: '0..*', label: 'places'`. Cardinalities are exactly `1`, `N`, `0..1`, `0..*`, or `1..*` and stay on their authored endpoints. Fields are conceptual; matching names and `key: :foreign` never infer a connector or physical SQL foreign key. ER accepts 2–6 entities, 1–6 fields each, 1–8 relationships, and at most one optional focal entity. See [entity-relationships.md](entity-relationships.md).
- Database schema: use `diagram :db_schema` with `table :orders, 'orders', schema: 'public' do ... end`, nested `column :customer_id, 'customer_id', sql_type: 'uuid', constraints: [:fk, :nn]`, literal `index 'idx_orders_customer_id'`, and `foreign_key :orders, :customer_id, references: [:customers, :id], on_delete: :restrict`. Column IDs are scoped per table. Foreign keys require explicit source `FK`, target `PK`/`UQ`, exact named row endpoints, and one of `cascade`, `restrict`, `set_null`, or `no_action`; nothing is inferred. The bounded model accepts 2–5 tables, 1–8 columns and 0–3 indexes per table, and 1–6 FKs. See [database-schemas.md](database-schemas.md).
- UML class: use `diagram :uml_class` with `class_type`, `abstract_class`, or `interface` blocks containing literal `attribute` and `operation` strings. Add `relation :child, :parent, kind: :inheritance`; composition/aggregation require `owner:`, while association requires both endpoint multiplicities. The six kinds are inheritance, realization, composition, aggregation, association, and dependency. Nothing is parsed or inferred. The bounded model accepts 2–7 classes, 1–8 relations, five members per compartment, and one optional focal class. See [uml-classes.md](uml-classes.md).
- Quadrant: use `diagram :quadrant`, declare `horizontal_axis low:, high:` and `vertical_axis low:, high:`, then add 2–12 `item` records with literal labels and explicit finite `x:`/`y:` coordinates in `[-1,1]`. Each coordinate must have absolute value at least 0.08. Zero or one item may be `focal: true`. Positions map linearly without scores, snapping, jitter, inference, or collision movement; labels must fit in the authored quadrant or rendering fails. See [quadrants.md](quadrants.md).
- Venn: use `diagram :venn`, declare exactly two or three `set` records, then name the complete topology with `intersection`. Two sets require their sole pair; three sets require all three pairs plus the triple. Members remain in authored order, while duplicate detection treats reordered members as the same topology. Zero or one overlap may be `focal: true`. Fixed equal circles encode topology only, never area, population, counts, or weights; measured labels fail rather than moving circles or changing membership. See [venn.md](venn.md).
- Loop: use `diagram :loop, direction: :clockwise`, declare exactly one `hub`, 5–8 `station` records, one `cycle` naming every station exactly once in displayed order, and exactly one explicit `write_back` per station. `cycle` declares every adjacent arc and the last-to-first closure. A list-form write-back expands only its named sources. Zero or one station may be focal; the dark hub means shared accumulated state. Do not infer station order, closure, spokes, skips, or branches. See [loops.md](loops.md).
- Swimlane: use `diagram :swimlane` with `lane :research, 'Research'`, ordered `stage :design, 'Design'`, and positional-label `activity :draft, 'Draft survey', lane: :research, stage: :design`; connect cards with `handoff :draft, :build_app`, with at most one optional `focal: true` handoff. Stages number contiguously; empty cells mean no work; there is one activity per cell, up to 1–6 lanes, 1–12 stages, 24 activities, and 24 handoffs. Swimlane is fixed horizontal/rightward and has no trigger, conversion, or parallel gateway. See [swimlanes.md](swimlanes.md).
- Process: use keyed lanes such as `lane :it, 'IT', key: 'IT'`, one `focal: true` stage and operation, and positional-label `operation :build_app, 'Build app', lane: :it, stage: :build, tool: 'CSPro', input: 'FL', output: 'TB'`. Payloads are only `LS`, `DB`, `TB`, `FL`, or `WB`; omitted/null means unknown, while first-stage input and last-stage output are rejected. Ordinary handoffs advance; one optional `trigger :pilot, :build_app, 'RETEST'` is neutral dashed and overrides focal styling. Tools stay in operation cards/descriptions; the legend reports numbered/focal steps, used payloads, and effective flows. Limits are 1–6 lanes, 1–12 stages, 24 operations, 24 ordinary handoffs plus one trigger, and exactly one focal stage/operation. See [processes.md](processes.md).
- Deployment: use `zone :prod, 'Production' do ... end` around `host`, `vm`, `pod`, `managed`, or `cdn`; each infrastructure node takes positive `replicas:` (default `1`) and an artifact block, such as `artifact 'api', version: 'v2.4.1'`. Connect node IDs with top-level `network :front_door, :api, protocol: 'HTTPS', port: 443, async: false, emphasis: false`; paths can be interleaved with zone declarations but are commonly written after the zones. Zones are real environment/network boundaries; IDs are globally unique; labels are optional and default from IDs; artifacts require nonblank versions. Strict JSON uses `zones`/`nodes`/`artifacts`/`paths` and rejects generic graph collections. The bounded model allows 3 zones, 6 infrastructure nodes, 9 artifact chips, 8 paths, and two combined emphasized nodes/paths. Dense routes or labels raise `LayoutError`; see the [deployment guide](deployments.md).
- IT current-state: use `phase :collect, 'COLLECT' do ... end` with nested `system :registry, 'Civil Registry', detail: 'CRVS', state: :external`; connect systems with `handoff :registry, :drive, 'EXCEL', style: :link, dashed: true`; add a footer service with `crosscut :identity, 'Identity Manager', detail: 'AD · LDAP · SSO'`. Systems use `state: :standard`, `:external`, or `:pain_point`; a pain-point endpoint makes touching handoffs accent. `dashed: true` draws the file-transfer treatment; there is no `manual` field. Source order controls forward/backward handoffs; a backward handoff requires an external endpoint and `dashed: true`. The renderer generates a legend from used semantics, while crosscut bars have no graph endpoints. The bounded horizontal model allows 2–4 phases, 1–5 systems per phase, 16 systems, 24 handoffs, two pain points, and three crosscuts. See the [IT current-state guide](it-current-state.md).
- High-level: use `diagram :high_level` with 3–5 phases; put `source :postgres, 'PostgreSQL', type: :db` in the first phase and `component :nifi, 'NiFi', role: 'COLL'` in later phases. Source/component labels may be omitted and humanize their IDs; component `role` is required. `connect :from, :to` is unlabeled and must move forward between phases. Mark exactly one component `focal: true`; add one optional `orchestrate :airflow, 'Airflow', targets: [...]` bar and `crosscut :identity, 'Identity', concern: 'Security'`. Orchestration defaults to concern `Orchestration`; its targets must be the top component in their phases so straight trigger drops remain visible. Crosscut concerns are required and pair to the vertical strip automatically. Source types are `db`, `ftp`, `web`, `legacy`, or `api`. The bounded model allows 3–5 phases, 1–4 sources, 1–2 later components per phase, 8 components, 12 links, one bar, two crosscuts, and one explicit focal. See the [high-level guide](high-level.md).
- Fishbone: use `diagram :fishbone`, declare one literal `effect`, then 2–5 `category` blocks with explicit `side: :above` or `:below` and 1–3 literal `factor` calls. Preserve investigative uncertainty: categories and factors are associated leads, not confirmed causes. Never invent or request root-cause, confirmation, confidence, blame, probability, causal-strength, or focal fields. At least one category belongs on each side and at most three fit per side. See the [fishbone guide](fishbones.md).
- Wardley: use `diagram :wardley` with 2–9 `component` records, each requiring a qualitative `evolution:` (`:genesis`, `:custom_built`, `:product`, or `:commodity`) and finite authored `visibility:` in `[0,1]`. Add 1–12 explicit `depends_on` pairs so every component is incident. Optional `evolving_to:` names only the adjacent band to the right and is limited to two components. Do not infer positions, dependencies, scores, runtime meaning, or movement. See the [Wardley guide](wardley-maps.md).
- Treemap: use 2–12 unique `item` records with nonnegative numeric values and at least one positive value. Area alone carries quantity. Keep zero as explicit data without a cell, and never invent a minimum area or `Other`; see [treemaps.md](treemaps.md).
- Sankey: declare exactly three stages and only positive adjacent-stage flows. Supply every node value and make first outgoing, middle incoming/outgoing, final incoming, and stage totals equal exactly. Name real Waste/Loss explicitly. Never infer a remainder or repair a narrow ribbon; see [sankeys.md](sankeys.md).
- Group only architecture/flowcharts: `group(:backend, 'Backend') { node :api; store :db }`.
- Labels default from IDs (`:background_worker` becomes “Background worker”). Override for acronyms.
- Prefer `flow` for chains, `edge` for branching or annotated links. Never author coordinates.
- At most two emphasized elements; everything else gets its meaning from labels and relationships.
- `direction: :down` is useful for document columns; `:right` for wide architecture diagrams. Dependency diagrams are ranked down with fixed direction.
- `style: :editorial/:ruby/:blueprint/:mono` selects a named preset. Existing diagrams keep editorial by default.
- `theme: :auto` follows OS/page; explicit `:light`/`:dark` stays fixed.
- 32 nodes/events, 64 edges/messages, 3 groups, 300 characters per text field. Dependency diagrams use their stricter 9-node/14-edge/four-rank/one-cycle budget; deployment diagrams use 3 zones/6 infrastructure nodes/9 artifact chips/8 paths and two combined focal elements; high-level diagrams use their stricter phase/source/component/link/bar/crosscut/focal budget; data-flow diagrams use 2–4 roles, 2–6 steps, 2–16 transfers, 20 handoffs, and one linked focal claim; access matrices use 2–5 roles, 2–10 components, 4–36 explicit cells, and at most one focal cell; swimlane/process diagrams use their lane, stage, cell, card, handoff, trigger, and focal budgets. Split dense diagrams on LayoutError. Use Mermaid explicitly for unsupported types.
- IT current-state diagrams use uppercase phase/handoff labels (14/8 characters), global IDs, and strict enum/boolean validation. Vertical layouts, icons, custom colors, side overrides, custom legends, and full editorial framing are deferred.
- SVG output is static, escaped, accessible, and has unique IDs. Default fonts have local fallbacks; no font or layout downloads.
- RSpec is the test framework. Public DSL examples are executable acceptance cases.

CLI from the checkout: `ruby -Ilib exe/slimgraph render diagram.rb -o diagram.svg`. JSON uses the same validated renderer; see [JSON input](json-input.md). `--style`/`--theme` override presentation. `ruby -Ilib exe/slimgraph styles` and `ruby -Ilib exe/slimgraph types` list supported choices. Standalone examples live in examples/standalone; StreamWeaver examples in examples/stream_weaver.
