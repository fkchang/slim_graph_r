# JSON input

## Quantitative charts

Bar, line, scatter, polar, and radar JSON use strict type-specific allowlists. Common quantitative keys are `type`, `title`, `description`, `style`, `theme`, `source_note`, `precision`, and `notation`. Optional strings must be nonblank, `precision` is an integer from 0 through 6, and V1 `notation` is `"plain"`. Explicit `null`, unknown keys, booleans encoded as strings, and numeric strings fail.

- Bar adds `unit`, optional `orientation` and `scale`, and required `categories`. A category allows only `id`, `label`, numeric `value`, and optional boolean `focal`.
- Line adds `unit`, required `x_axis`, optional `scale`, and required `series`. Each point contains exactly numeric `value`, or exactly `{"gap":true,"reason":"..."}`.
- Scatter adds required `x_unit`, `y_unit`, `x_scale`, `y_scale`, and `points`. A point allows only `id`, `label`, numeric `x`, numeric `y`, optional boolean `focal`, and optional boolean `annotate`.
- Treemap adds required `unit` and `items`. Each item allows only `id`, `label`, numeric nonnegative `value`, and optional boolean `focal`; at least one value is positive.
- Sankey adds required `unit`, `stages`, `nodes`, and `flows`, plus optional `balance` whose only value is `"strict"`. Stage records allow `id` and `label`; node records allow `id`, `stage`, `label`, and positive numeric `value`; flow records allow `from`, `to`, and positive numeric `value`.

JSON numbers normalize to `BigDecimal` before validation and geometry. See the paired [bar](../examples/standalone/bar.json), [line](../examples/standalone/line.json), [scatter](../examples/standalone/scatter.json), [treemap](../examples/standalone/treemap.json), [Sankey](../examples/standalone/sankey.json), [polar](../examples/standalone/polar.json), and [radar](../examples/standalone/radar.json) examples.

Polar requires `unit`, exact `{min: 0, max: positive}` `scale`, and 4–8 `categories` containing only `id`, `label`, `value`, and optional boolean `focal`. Radar requires the same unit/scale plus 3–5 ordered `criteria` and 2–5 ordered `entities`; every entity `values` object contains exactly the criterion IDs in criterion order. Missing, extra, null, negative, mixed-scale, fill, geometry, and normalization fields fail. See [polar-charts.md](polar-charts.md) and [radar-charts.md](radar-charts.md).

`slimgraph render input.json -o output.svg` builds the same model as the Ruby DSL. JSON is parsed and validated, never evaluated as Ruby. For library use, require `slim_graph_r/document` and call `SlimGraphR::Document.from_json(json_string)`.

```json
{
  "type": "architecture",
  "title": "Request handling",
  "style": "ruby",
  "theme": "light",
  "groups": [{"id": "backend", "label": "Backend"}],
  "nodes": [
    {"id": "client", "kind": "external"},
    {"id": "api", "label": "API", "emphasis": true, "group": "backend"},
    {"id": "db", "label": "Database", "kind": "store", "group": "backend"}
  ],
  "edges": [{"from": "client", "to": "api"}, {"from": "api", "to": "db", "label": "Query"}]
}
```

## Fields

- Required `type`: architecture, flowchart, sequence, timeline, org_chart, state, dependency, deployment, it_state, high_level, tree, nested, layers, pyramid, medallion, swimlane, process, gantt, kanban, journey, story_map, data_flow, dp_integration, dp_security_matrix, er, db_schema, uml_class, quadrant, venn, loop, fishbone, or wardley.
- Optional `title`, `description`, `direction` (right/down), `theme` (light/dark/auto), `style` (editorial/ruby/blueprint/mono), `scale` (timeline: auto/date/ordered).
- `nodes`: `id` (required), `label`, `detail`, `kind` (service/store/external/decision/start/finish/merge), `emphasis` (boolean), `group` (a declared group ID).
- `edges`: `from`, `to` (required node IDs), `label`, `dashed` (boolean), and sequence-only `kind` (call/return/async/success). For sequence diagrams these are messages, in chronological order.
- `groups`: `id` (required), `label`. Only architecture and flowchart support groups. Nodes must reference an existing group; nested groups are not supported.
- `events`: `date`, `label` (required), `detail`, `emphasis` (boolean). Only timeline accepts events. Timeline does not accept nodes, edges or groups. With `scale: :date`, every date must parse as YYYY-MM-DD and events are spaced by elapsed days with axis ticks. With `scale: :ordered`, date strings are captions and author order is preserved. `:auto` chooses date scaling only when every event parses.
- Org-chart node fields are `invoke` (string), `scope` (string), and `unavailable` (boolean), in addition to the shared `id`, `label`, `detail`, `kind`, and `emphasis` fields. `invoke` and `scope` are optional but cannot be blank; `unavailable` must be a JSON boolean. Org charts also accept top-level `escalations` (`{"label":"Unowned work","to":"intake"}`), `approvals` (`{"label":"Production release","by":"lead"}`), and `setup_gaps` (`{"label":"Name a release gate","for":"lead"}`); each reference must name an existing node.
- State-machine fields are `states`, `initial`, `finals`, and `transitions`. A state has `id`, optional `label`, and optional boolean `emphasis`. A transition has `from`, `to`, required nonblank `on`, and optional nonblank `guard` and `action`. State machines require one initial state, one or two finals, and reject generic `nodes`, `edges`, `groups`, `events`, `steps`, `escalations`, or `approvals` fields, including empty arrays. See the [state-machine guide](state-machines.md) for the complete Ruby/JSON pair and bounded topology rules.
- Dependency nodes use `id` and optional `label`; an external node must use `kind: "external"` plus nonblank `version` and `registry`. Dependency edges use `from` (dependent), `to` (requirement), and optional boolean `cycle`. Dependency diagrams reject generic node fields such as `detail`, `emphasis`, or `group` and reject `groups`, `events`, `states`, `steps`, `escalations`, and `approvals`. See the [dependency guide](dependencies.md) for the complete Ruby/JSON pair and bounded topology rules.
- Deployment JSON uses `zones`, each with `id`, optional `label`, and nonempty `nodes`; each node uses `id`, optional `label`, `kind` (`host`, `vm`, `pod`, `managed`, or `cdn`), positive integer `replicas` (default `1`), optional boolean `emphasis`, and nonempty `artifacts`; each artifact requires nonblank `name` and `version`; `paths` require `from`, `to`, `protocol`, and an integer `port` in `1..65535`, with optional boolean `async` and `emphasis`. Deployment rejects generic `nodes`, `edges`, `groups`, `events`, `states`, `steps`, `escalations`, and `approvals`. See the [deployment guide](deployments.md) for the complete Ruby/JSON pair and bounded containment/layout rules.
- Database-schema JSON uses required `tables` and `foreign_keys`. A table requires `id`, `label`, and 1–8 `columns`, with optional nonblank `schema`, 0–3 `indexes`, and one literal integer `overflow_columns` from 1 through 99. The overflow count renders `+ N more columns` and never creates concrete fields. Each column requires `id`, `label`, `sql_type`, and a `constraints` array containing unique values from `pk`, `fk`, `uq`, and `nn`. A foreign key requires `from_table`, `from_column`, `to_table`, `to_column`, and `on_delete` from `cascade`, `restrict`, `set_null`, or `no_action`. Its source column must declare `fk`, and its target must declare `pk` or `uq`. See [database-schemas.md](database-schemas.md).
- UML-class JSON uses required `classes` and `relations`. Each class requires `id`, `label`, and `kind` (`class`, `abstract_class`, or `interface`); optional `focal` is boolean and `attributes`/`operations` are arrays of at most five literal nonblank strings. Relations require `from`, `to`, and one of six `kind` values. Composition/aggregation alone require endpoint `owner`; association alone requires both `from_multiplicity` and `to_multiplicity` from `1`, `0..*`, or `1..*`. See [uml-classes.md](uml-classes.md).
- Quadrant JSON uses required `horizontal_axis`, `vertical_axis`, and `items`. Each axis object has only required nonblank string `low` and `high` phrases. Each of 2–12 items requires unique string `id`, string `label`, and finite numeric `x`/`y` in `[-1,1]` with absolute value at least 0.08; omitted boolean `focal` means false and at most one may be true. Generic graph, score, color, midpoint, direction, null, and unknown fields fail. Positions map linearly and labels never move their dots. See [quadrants.md](quadrants.md).
- Venn JSON uses required `sets` and `intersections`. Each of exactly two or three sets has only required nonblank string `id` and `label`. Every intersection has a two- or three-member `sets` string array, required nonblank `label`, and optional boolean `focal`; two sets require the sole pair, while three require all pairs and the triple exactly once. Reordered members are duplicate topology, though authored order is preserved in descriptions. Nulls, unknown/cross-type fields, quantities, weights, radii, positions, colors, omitted regions, unknown members, duplicate topology, and a second focal overlap fail. See [venn.md](venn.md).
- Loop JSON requires `direction: "clockwise"`, one `hub`, 5–8 `stations`, one `cycle` array naming every station exactly once in displayed order, and `write_backs` containing exactly one explicit station-to-hub record per station. Hub and stations accept only `id`, `label`, and optional `sublabel`; stations also accept optional boolean `focal`, with at most one true. Write-backs accept only `from`, `to`, and optional literal `label`. The cycle authorizes adjacent arcs and closure; records never infer closure, spokes, skips, or branches. See [loops.md](loops.md).
- Fishbone JSON requires an `effect` object containing only a nonblank string `label`, plus 2–5 `categories`. Each category contains only unique string `id`, nonblank string `label`, `side` (`above` or `below`), and 1–3 ordered nonblank string `factors`. At least one category must appear on each side, with at most three per side and 18 factors total. Direction, generic graph records, root-cause/confirmation/confidence/blame/probability/causal-strength fields, focal fields, nulls, and arbitrary geometry are rejected. See [fishbones.md](fishbones.md).
- Wardley JSON requires `components` and `dependencies`. Each of 2–9 components contains only unique nonblank string `id`, nonblank string `label`, `evolution` (`genesis`, `custom_built`, `product`, or `commodity`), finite numeric `visibility` in `[0,1]`, and optional `evolving_to` naming only the adjacent band to the right. The 1–12 dependencies contain only `from` and `to`, reference known components, are unique, and make every component incident. At most two components evolve. Direction, generic graph records, free x/y, scores, numeric ticks, focal fields, labels, colors, runtime semantics, nulls, and unknown keys fail. See [wardley-maps.md](wardley-maps.md).

- IT current-state JSON uses top-level `phases`, `handoffs`, and `crosscuts`. Each phase has required `id`, optional `label` (default: uppercase humanized ID), and required `systems`; each system has required `id`, optional `label` (default: humanized ID), optional `detail` (default: `nil`), and optional `state` (`standard`, `external`, or `pain_point`, default `standard`). Each handoff has required `from`, `to`, and `label`, optional `style` (`neutral`, `link`, or `accent`, default `neutral`), and optional boolean `dashed` (default `false`). Each crosscut has required `id`, optional `label` (default: humanized ID), and optional `detail` (default: `nil`). `title` defaults to `Diagram`, `direction` to `right`, `theme` to `light`, and `style` to `editorial`; `subtitle` and `eyebrow` are optional top-level presentation fields. The type rejects generic graph collections and fields from other diagram types. See the [IT current-state guide](it-current-state.md) for the complete Ruby/JSON pair and bounded horizontal-layout rules.
- High-level JSON uses top-level `phases`, `connections`, optional `orchestration`, and optional `crosscuts`. Each phase has required `id`, optional `label` (humanized by default), optional `columns` (default `1`), and `sources`/`components` arrays. The first phase contains sources only; later phases contain components. Sources require `id` and `type` (`db`, `ftp`, `web`, `legacy`, or `api`); `label` and `detail` are optional, and labels default from IDs. Components require `id` and nonblank `role`; `label` and `detail` are optional, `role` is limited to eight characters, and boolean `focal` defaults to `false`. Connections contain only `from` and `to`. Orchestration has `id`, optional `label` and `detail`, optional `concern` (default `Orchestration`), and nonempty `targets`; each crosscut has `id`, optional `label` and `detail`, and required distinct `concern`. `cluster` is an optional diagram label defaulting to `Cluster`. Unknown, null, cross-type, same-phase, backward, query, and labelled-edge fields fail. See the [high-level guide](high-level.md).
- Tree JSON uses one required recursive `root` object. Each tree node requires `id` and accepts optional `label`, `detail`, boolean `focal` (default `false`), and `children`; omitted `children` means a leaf. Labels default from IDs. The tree requires one root, globally unique IDs, direct parent/child tiers, depth 1–4 including the root, at most five nodes per tier, at most five children per parent, and zero or one focal node. `direction` defaults to `down` and accepts `down` or `right`. Explicit nulls, unknown or cross-type fields, malformed recursion, duplicate IDs, and a second focal node fail. See the [tree guide](trees.md).
- Nested-containment JSON uses one required recursive `scope` object with required `id` and optional `label` (default humanized from the ID) and nested `scope`. The chain has one outer scope and 3–5 uninterrupted levels; sibling scopes and extra content fail. Direction is fixed `down`. Explicit nulls, arrays in place of a scope, unknown or cross-type fields, and duplicate IDs fail. The innermost scope receives automatic focal treatment. See the [nested-containment guide](nested-containment.md).
- Layer-stack JSON uses top-level `layers` plus optional `axis` (default `Abstraction`) and `indicator` (default `up`, only `up` or `down`). Each layer requires `id` and `index`; `label`, `detail`, and boolean `focal` (default `false`) are optional. Four to six layers are required, IDs and indices are unique, and exactly one layer is focal. Numeric indices, including `L4`, must be one contiguous ascending or descending sequence; all-semantic indices are allowed, but numeric and semantic forms cannot be mixed. See the [layer-stack guide](layer-stacks.md).
- Pyramid JSON uses `levels` plus optional `orientation` (default `pyramid`), `mode` (default `hierarchy`), and `unit`. A level requires `id` and accepts `label`, `detail`, boolean `focal` (default `false`), and measured `from`/`to` values. Hierarchy accepts only the unquantified fields and only the upward pyramid; measured mode requires a shared nonblank unit, an initial positive finite `from`, finite nonnegative chained boundaries, and `to <= from`. Equal boundaries and a zero tail are valid. Widths remain exactly proportional and unplaceable labels use outside leaders or raise `LayoutError`; `direction` and generic graph fields are rejected. See the [pyramid guide](pyramids.md).
- Medallion JSON uses `tiers`, `promotions`, and optional `write_paths`. A tier requires `id`, `bucket`, `tool`, `format`, `writer`, and one or two `examples`; `label`, boolean `focal`/`archive`, and `concern` (`security`, `quality`, `product`, or `analysis`) are optional. Exactly one focal tier is required; there may be at most one archive and it must be final. Promotions must cover each adjacent tier exactly once with uppercase labels of at most 14 characters. At most two tiers/paths may carry concerns and at most two write paths are allowed. Concerned incoming arrows match the target concern, focal styling wins, and archive uses the dashed lifecycle treatment. Fixed card, arc, and write-path lanes raise `LayoutError` when measured text cannot fit. See the [medallion guide](medallions.md).
- Swimlane JSON uses top-level `lanes`, `stages`, `activities`, and `handoffs`. Lanes and stages require `id` and may use `label` (humanized defaults); each activity requires `id`, `lane`, and `stage` and may use `label`; each handoff requires `from` and `to` and may use boolean `focal` only for swimlanes. The model requires at least one activity, allows 1–6 lanes, 1–12 stages, 24 activities, one activity per lane/stage cell, and 24 handoffs. Stages number in declaration order, ordinary handoffs advance through stages, and a swimlane has zero or one focal handoff. Direction is fixed to `right`; generic graph fields, same-stage/backward handoffs, unknown fields, duplicate cells/IDs, and null values fail. See the [swimlane guide](swimlanes.md).
- Process JSON uses the same `lanes`, `stages`, and `handoffs` fields plus `operations` and an optional `trigger` object `{from,to,label}`. Process lanes require unique rendered `key` values of 1–3 characters; stages accept boolean `focal`; operations require `id`, `lane`, `stage`, and nonblank `tool`, with optional `label`, `detail`, boolean `focal`, and `input`/`output` from `LS`, `DB`, `TB`, `FL`, or `WB`. Omitted or null payloads mean unknown; supplied first-stage input or last-stage output is rejected. The model requires exactly one focal stage and operation, allows 24 operations, 24 ordinary handoffs, and one optional labelled backward trigger. Ordinary handoffs advance; triggers are neutral dashed return edges. Direction is fixed to `right`; generic graph fields, same-stage/backward ordinary handoffs, unknown fields, duplicate cells/IDs, and invalid keys or payloads fail. See the [process guide](processes.md).
- Gantt JSON uses required top-level `phases`, `milestones`, and `markers` arrays. Phases contain required `id`, `label`, and `tasks`; tasks require `id`, `label`, complete Gregorian `start`/`finish` dates, and optional boolean `focal`. Milestones require `id`, `label`, and point date `on`, with optional `phase` naming an existing phase; markers require `id`, `label`, and `on` and never accept `phase`. Tasks use the half-open `[start, finish)` interval, so `finish` must be after `start`. The bounded model allows 0–4 phases, 0–12 tasks, 0–8 milestones (at least one when there are no tasks), 0–2 markers, and one focal task. Dates use one exact elapsed-day scale; phase/task declaration order is retained, and fixed calendar direction rejects `direction`. Same-track milestone diamonds under 12px overlap fail; close marker lines may render when measured geometry is clear. See the [Gantt guide](gantt.md).
- Kanban JSON uses required top-level `columns`; each column requires `id`, `label`, and `cards`, with optional positive integer `wip_limit`. Cards require `id` and `label` and accept optional nonblank `ticket`, `owner`, one of `default`/`blocked`/`waiting`/`done` as `state` (default `default`), and boolean `focal` (default `false`). Declaration order is preserved and counts derive from displayed cards. A supplied limit renders the actual `n/limit` and accepts violations; there are no connectors or inferred states. The bounded model allows 2–5 columns, 0–4 cards per column, 0–12 cards total, and one focal card. More cards or unplaceable measured text raises `LayoutError` without aggregation or dropping content. See the [Kanban guide](kanban.md).
- Journey JSON uses required `persona` and `stages`. A stage requires `id`, `label`, `action`, and one explicit ordinal `sentiment` (`high`, `medium_high`, `neutral`, `medium_low`, or `low`), with optional `touchpoint` and up to two `pains`. The bounded model allows 2–6 declaration-ordered stages and exactly one unique lowest-sentiment trough; pain markers are allowed only on that trough. The fixed curve is an ordinal sequence, not a measured score, and direction, numeric sentiment, generic graph fields, nulls, and unknown fields fail. See the [journey guide](journeys.md).
- Story-map JSON uses required `persona`, `activities`, and `releases`. Activities require 1–2 ordered `steps`; releases require at least one `story`, exactly one non-final `cut: true`, and each story must reference an existing activity. `estimate` and `ticket` are optional authored nonblank metadata; at most one story may set `risk: true`. The bounded model allows 2–5 activities, 2–3 releases, 12 stories total, and four stories per release. Release labels are literal text even when date-like; no state, sentiment, dependency, priority, or calendar meaning is inferred. See the [story-map guide](story-maps.md).
- Data-flow JSON uses required `roles`, `steps`, `transfers`, and `handoffs`. Roles require `id`, `label`, and a unique uppercase `key` of one to three characters. Steps require `id` and may set boolean `focal`; transfers require `id`, `role`, `step`, and nonblank `tool`, with optional `label`, boolean `focal`, and `input`/`output` from `web`, `dataset`, `table`, `file`, or `stream`. Handoffs require `from`, `to`, and `kind` (`ordinary`, `trigger`, `focal`, or `publish`); only the focal handoff accepts its required uppercase `label`. The bounded model allows 2–4 roles, 2–6 steps, 2–16 transfers, and 20 handoffs, with exactly one linked focal step/transfer/handoff claim. Empty cells remain empty, payloads are never inferred from handoffs or adjacent cells, and direction is fixed to the horizontal role × stage grid. See the [data-flow guide](data-flows.md).
- DP-integration JSON uses `sources`, one `platform` with ordered `rows` (`bar` or one `row`), `consumers`, `layer_services`, and `wires`. Sources use `database`, `file_drop`, `mail`, or `legacy`; consumers use `analytics`, `web`, or `api`; layer services use `identity`, `observability`, `backup`, or `secrets`. Wires use `ordinary`, `federated`, `trigger`, or `serve`, with literal protocols on every non-trigger wire. The bounded model allows 0–6 sources and consumers, 2–6 platform components, 0–3 layer services, and 20 wires, with exactly two focal components and one serving component. Layer services attach to the platform boundary. Unknown, null, cross-type, inferred, and direct layer-service/component fields fail. See the [platform-integration guide](platform-integrations.md).
- DP-security-matrix JSON uses required `roles`, `components`, and `permissions`. Roles require `id` and `label` and may carry `code`; components require `id` and `label` and may carry `hint`. Every component × role coordinate requires exactly one permission with `component`, `role`, and `level` (`admin`, `write`, `read`, `deny`, or `unknown`). An omitted `label` receives only that explicit level's deterministic display label. Boolean `focal` defaults false; `note` is allowed only on the zero-or-one focal permission. The bounded model allows 2–5 roles, 2–10 components, and 4–36 cells. Omission, inheritance, connectors, generic graph fields, unknown keys, nulls, duplicate coordinates, and invalid booleans fail. See the [access-matrix guide](access-matrices.md).
- ER JSON uses required `entities` and `relationships`. Each entity requires `id`, `label`, and 1–8 `fields`; optional `kind` is exactly `entity`, `aggregate_root`, or `join_table`, and boolean `focal` defaults to false. Each field requires `id` and `label`, with optional `key` exactly `primary` or `foreign`, and optional literal nonblank `type` and `qualifier`; field IDs are scoped to their owning entity. These conceptual annotations never create physical SQL constraints or foreign keys. Each relationship requires `from`, `to`, `from_cardinality`, and `to_cardinality`, with optional nonblank `label`; cardinalities are exactly `1`, `N`, `0..1`, `0..*`, or `1..*`. The bounded model accepts 2–6 entities, 1–8 relationships, and at most one focal entity. Generic graph and physical-schema keys, nulls, self/duplicate relationships, and inferred relationships fail. See [entity-relationships.md](entity-relationships.md).

All supplied text fields must be strings, not null. Required identifiers must be nonblank. Optional fields can be omitted. Unknown keys and incorrectly typed fields are errors. Fields are limited to 300 characters; input is limited to 1 MiB. Start/finish/merge kinds are flowchart-only. Decisions require labeled exits and at most three outgoing edges; starts cannot have incoming edges, finishes cannot have outgoing edges, and merges require two or three inputs and one output. Merge names remain in accessible descriptions, while the visible symbol is a small unlabeled dot. Merge detail text and emphasis are rejected.

All Ruby model limits also apply, including valid references, distinct IDs, complexity budgets, and emphasis limits.

Org-only fields and arrays are strict: `invoke`, `scope`, `unavailable`, `escalations`, and `approvals` raise on every other diagram type, even when an array is empty. Unknown keys continue to raise. Org charts allow at most 12 visible nodes, four tiers (root is tier 1), five direct reports per parent, one emphasized node, and two combined escalation/approval callouts. A child may have one incoming reporting edge; cycles are errors. Disconnected roots and forests are supported. Rules are rendered in a separate footer strip and are not graph nodes. See the [org-chart guide](org-charts.md) for a complete Ruby/JSON pair.

State machines allow two to twelve states, at least one transition, at most twice as many transitions as states, four incoming/four outgoing transitions per state, one transition per ordered pair, one self-loop per state, one simple two-to-four-state directed cycle, and two emphasized states. Every state must be reachable from the initial state and able to reach a final; finals have no outgoing transitions. A route or measured label that cannot be placed clearly raises `LayoutError` rather than silently crossing or obscuring content. See [state-machines.md](state-machines.md).

Dependency diagrams use a fixed downward direction. Their bounded limits are 9 nodes, 14 edges, four ranks, one marked cycle, and two accent elements. A marked edge must close a real cycle and removing it must leave a DAG; one-parent branching hierarchies use `:tree` with nested `root`/`child` blocks. Dense routes or labels raise `LayoutError` rather than being silently crossed or clipped. See [dependencies.md](dependencies.md). Sequences and timelines have fixed layouts; the graph `direction` option applies to architecture, flowchart, org_chart, state, and tree. Swimlane and process layouts are fixed horizontal actor lanes with rightward stages; journey and story-map layouts likewise preserve their authored horizontal order and reject direction overrides.

Deployment diagrams use fixed three-level containment (`zones` > infrastructure `nodes` > versioned `artifacts`). Their bounded limits are 3 zones, 6 infrastructure nodes, 9 artifact chips, 8 paths, and two combined emphasized nodes/paths. Unknown fields, empty zones, artifact-less nodes, unversioned artifacts, duplicate IDs/paths, unknown endpoints, invalid replicas or ports, and routes or labels that cannot be placed faithfully raise errors. See [deployments.md](deployments.md).
High-level diagrams use 3–5 horizontal phases, at most five columns total, 1–4 sources in the first phase, 1–2 components in each later phase, 8 components, 12 forward data links, three outgoing links per source/component, one orchestration bar, two crosscuts, and exactly one explicit focal component. Orchestration targets must be the top component in their phase so a straight trigger drop remains visible. Reserved concern labels are not horizontal phases; icons, custom colors, manually authored vertical concerns, query/backward/same-phase links, edge labels, side overrides, unclustered layouts, and editorial-card variants remain outside this slice. Unplaceable routes or measured text raise `LayoutError`.

IT current-state diagrams require 2–4 phases, 1–5 systems per phase, at most 16 systems, 24 handoffs, two pain points, and three crosscuts. Phase labels are uppercase and at most 14 characters; handoff labels are uppercase and at most 8. IDs are globally unique. Source order determines forward/backward direction; a backward handoff requires an external endpoint and `dashed: true`. Unknown fields, duplicate IDs, missing references, self-handoffs, invalid states/styles, non-boolean `dashed`, and routes or labels that cannot be placed faithfully raise clear errors. Vertical layout, icons, custom colors, side overrides, caller-authored legends, and full editorial framing are outside this bounded slice. See [it-current-state.md](it-current-state.md).

The CLI defaults to JSON for stdin. Use `--input-format ruby` to explicitly execute Ruby from stdin. A file's extension normally selects its input format; `--input-format` overrides it.

CLI overrides `--style` and `--theme` apply to both Ruby and JSON documents without mutating the original diagram. Timelines also accept `--scale auto|date|ordered`. Date mode requires complete, valid Gregorian YYYY-MM-DD strings, sorts chronologically, and groups same-day events at one marker. Relative/partial dates are captions in auto mode. See [timeline.md](timeline.md). Output format defaults to SVG for stdout or is inferred from the output filename; use `--format svg|html` to specify it. Only SVG/HTML are supported; PNG is on the roadmap.

Exit statuses: 0 success, 1 document/render/I/O error, 2 command-line usage error. Renderer diagnostics go to stderr. Ordinary Ruby `puts` output is redirected to stderr while evaluating the document; arbitrary trusted Ruby can still explicitly write to OS file descriptors or exit the process.


## Sequence steps (0.4.0)

A sequence may use `steps` instead of flat `edges`; supplying both is an error. Each step has exactly one action:

- `{"message":{"from":"a","to":"b","label":"Call","kind":"call"}}`
- `{"activate":"b","steps":[...]}`
- `{"alt":[{"guard":"valid","steps":[...]},{"guard":"else","steps":[...]}]}`
- `{"opt":"if needed","steps":[...]}`
- `{"loop":"for each item","steps":[...]}`

Message fields are the same as flat edges. Unknown fields, null strings, malformed actions, and contradictory kind/dashed flags are errors. Guards and actor IDs must be nonblank. JSON parsing caps nested input at eight levels and 64 actions; the stricter model limits still apply: five participants, twelve messages, one alt or two opt/loop frames, no nested frames, and three activation levels per actor. Activation/frame scopes must contain messages.

See the [complete nested JSON example](../examples/standalone/sequence_frames.json) and [sequence guide](sequence.md). The parser never evaluates input as Ruby.
